## 0. 先用两分钟把这件事想明白

**现在的处境：** 网站是能跑的，但它没准备好让五个人同时动。

为什么？因为现在的代码是「几个大文件」：所有页面挤在 `public/app.js` 里、所有接口挤在 `src/server.js` 里、所有表挤在 `src/db.js` 里。五个人一起改，等于五个人同时改同一个文件，Git 每次合并都要吵架。

**已经做完的事：** 把那几个大文件按「谁的活」拆开了，并且给每个人**划好了地盘**——自己的文件夹、自己的接口前缀、自己的数据库表、自己的页面文件、自己的样式文件、自己的端口、自己的测试脚本。

拆完之后：

| | 拆之前 | 拆之后 |
|---|---|---|
| `public/app.js` | 4254 行，所有人都在里面加东西 | **43 行**，只剩装配，平时不用动 |
| `public/style.css` | 3118 行，改一行都怕碰坏别人 | 24 行 `@import`，**一人一个分片文件** |
| `src/server.js` | 1837 行，所有接口都在这 | **86 行**，只剩装配 |
| `src/db.js` | 940 行，所有表都在这 | 41 行门面 + 建表 SQL 单独一个文件 |
| 新功能写在哪 | 「随便找个地方塞进去」 | `src/modules/<你的名字>/` |

**关键：拆的时候一个字的行为都没改。** 这是有证据的，不是嘴上说说——见第 5 节。

**隐喻：** 现在的代码是「一个毛坯大房间，五个人要同时在墙、地、天花板施工」。预铺骨架做的事是**先砌好五道隔断墙、拉好插座、标好哪根管是你的**。你进自己的房间，随便怎么装修，别人不会受影响。

## 1. 拿到代码 + 在自己电脑上跑起来

### 1.1 拿代码

先在 GitHub 上把 `v2-skeleton` 分支合进 `main`（或者直接基于 `v2-skeleton` 开工，看你）。然后：

```bash
git clone https://github.com/RyuriHime/Blog.git
cd Blog
git checkout v2-skeleton      # 还没合并进 main 就切到这个分支
```

**⚠️ 第一条纪律：永远不要推 `main`。**

服务器上有个定时任务，它会自动拉 `main` 并部署到真实线上。你推 `main` = 你直接上线了。你自己的功能分支叫 `feat/feed`、`feat/doc` 这样就行。

### 1.2 检查 Node 版本

```bash
node -v
```

必须是 **v22.5 或更高**（项目用 Node 自带的 `node:sqlite`，低版本没有这个模块）。项目**没有任何第三方依赖，不需要 `npm install`**，克隆下来就能跑。

### 1.3 起你自己的本地服务

每个人占一个端口，互不打架：

| 你 | 端口 | 数据库 |
|---|---|---|
| P1 动态 | 3511 | `data/p1.db` |
| P2 积木帖子 | 3512 | `data/p2.db` |
| P3 AI | 3513 | `data/p3.db` |
| P4 团队 | 3514 | `data/p4.db` |
| P5 界面 | 3515 | `data/p5.db` |

**Windows（PowerShell）：**

```powershell
$env:PORT='3512'; $env:DB_FILE='data/p2.db'; node src/server.js
```

**macOS / Linux：**

```bash
PORT=3512 DB_FILE=data/p2.db node src/server.js
```

浏览器打开 `http://127.0.0.1:3512` 就能看到网站。数据库文件不存在会**自动建好并灌一批演示数据**（5 个板块、4 个演示账号、8 篇帖子）。

演示账号：`admin` / `admin123`（站长），`alice`、`bob`、`carol` / `demo1234`。

> **为什么要每个人一个库？** 不然你改表结构、他改表结构，两个人互相把对方的库搞坏，还查不出是谁干的。

### 1.4 AI 功能（只有 P3 需要）

不配也行，网站照常跑，只有 AI 那几个接口会返回「未配置」。要配就再设三个环境变量：

```
AI_API_KEY=sk-你的key
AI_BASE_URL=https://api.deepseek.com/v1
AI_MODEL=deepseek-chat
```

**⚠️ 第二条纪律：这些 key 绝对不许提交进仓库。** `.gitignore` 已经排除了 `.env`，但你如果硬写进 `.js` 文件里，它就上 GitHub 了。上线时 key 是**由服务器的环境变量注入**的，跟代码仓库完全分开——所以仓库里出现任何真实 key，都只有一个可能：有人写错了。

### 1.5 改完怎么验证

**每次准备提交之前，至少跑这三条：**

```bash
node scripts/check-skeleton.mjs    # 我的模块能单独拆掉吗？薄入口有没有变胖？
node scripts/check-golden.mjs      # 我有没有把现有行为改坏？
node scripts/smoke.mjs             # 后端接口还能正常跑吗？
```

看到 `通过 N 项，问题 0 项` / `通过 N 项，差异 0 项` 才算过关。**任何一条红了都别提交**。

想看全部测试跑什么：

```bash
npm test      # 有些人环境里 npm 不好使，那就逐个 node scripts/xxx.mjs 手动跑
```

## 2. 你的地盘在哪（每个人的文件清单）

**核心规矩：只动「你的」那一列里的文件。** 想做别的列的事，先在群里说一声，别自己动手。

### 2.1 五个人的完整归属表

| | **P1 动态** | **P2 积木帖子** | **P3 AI** | **P4 团队** | **P5 界面** |

| **样式** | `public/css/31-feed2.css` | `public/css/41-doc.css` | `public/css/94-ai-edit.css` | `public/css/86-team.css` | 改现有 `public/css/*` |

**文件名可以改**，但**位置必须在你的目录里**：后端一律在 `src/modules/<你的名字>/` 下面，前端页面一律在 `public/views/` 下面，样式一律在 `public/css/` 下面。

### 2.2 谁都不能碰的（要改先说一声）

- `src/core/*` —— 框架层（路由、数据库连接、权限门、出参格式、静态分发）。**这是全站的地基。**
- `src/modules/core/*` —— 现有论坛本体（认证、帖子、回复、社交、通知、管理）。`src/modules/core/routes-a.js` 到 `routes-d.js` 就是原来 `server.js` 里那 49 条接口。
- `src/store.js` —— 现有数据访问层（所有现成的 SQL 都在这）。
- **现有的** `public/views/*.js`、**现有的** `public/css/*.css` —— P5 例外，P5 的工作就是改这些。

**为什么这么严？** 因为 `check-golden.mjs` 会拿 96 条固定请求去比对「网站行为有没有变」。你改了 core，动了别人的东西，指纹一比对就不对了——测试会红，但**你很难知道是哪儿红的**。所以规矩是「别动」，不是「小心点动」。

### 2.3 五个人的活有没有先后依赖

有，但不多，记住这三条就够：

```
P2（积木帖子）是地基 ──→ P3 要读 documents / document_blocks 两张表
                    └─→ P4 的「仅团队可见」要判断文档的可见范围

P1（动态）独立 ──→ 只是「引用」帖子，不拥有 posts

P5（界面）独立 ──→ 只改观感，不碰数据
```

**所以 P2 是关键路径。** 时间紧就给 P2 加人，不要给 P4 加人。

**注意 P4 的坑：** 你们要的「多人共同编辑」，现在的网站是「谁最后保存谁算数」——没有版本号、没有冲突提示、没有任何实时通道。**先做「版本号 + 冲突提示」（改动小、解决真痛点），实时协同放第二期。** 别一上来就上 WebSocket，那是个坑。

**P3 的注意：** `/api/ai/*` 这个前缀已经被 `forum-ai` 那个包占了 8 条路由（`/api/ai/posts/:id`、`/api/ai/site`、`/api/ai/ask` 等）。你**只做加法**，别去改它那 8 条，也别把路径撞了。

## 3. 靠 AI 写代码的六条经验（这部分最实用）

因为大家都是 vibe coding，这部分单独讲。

### 经验 1：先把「契约」贴给 AI，再让它写

AI 最大的毛病是**它不知道你的项目已经定死了什么**，于是它会自己发明一套。比如你让它「做个动态功能」，它会给你建一张叫 `posts_v2` 的表、接口返回 `{success: true, result: ...}`——跟现有全站的格式完全不一样，合并的时候你就要手工改。

**开始之前先把这段贴给它**（原文照抄，别概括）：

```
这个项目已经冻结了下面这些约定，你写代码必须严格遵守，不许自己发明：

1. 模块形状：每个 src/modules/<名字>/index.js 只导出
   { name, apiPrefix, owns, reads, install(ctx) }
   - owns 是「这个模块建的表」，精确表名
   - 建表用 ctx.schema.add(表名, SQL, '模块名')，不要自己 CREATE TABLE
   - 登记路由用 ctx.routes.add(method, pattern, handler)

2. 响应格式（一个字都不许变）：
   成功  { "ok": true, "data": {…} }
   失败  { "ok": false, "error": { "code": "…", "message": "…" } }
   错误代号只许用这些：bad_request(400) unauthenticated(401) banned(403)
   forbidden(403) owner_only(403) not_found(404) conflict(409)
   rate_limited(429) ai_not_configured(503) ai_timeout(504)

3. 我的接口前缀是 /api/xxx/*，我只在这个前缀下加路由。

4. 我不许 import 别的模块的文件，也不许自己连数据库。
   要数据就用 ctx.db 直接读表，或者用 ctx.store 里已有的方法。

5. 可见范围的枚举已经冻结：scope = 'public' | 'followers' | 'team' | 'private'

6. 不许用 node --test 写测试（受限环境下会 EPERM）。
   照抄现有写法：自己起临时服务器 + 自己数断言，最后打印「通过 N 项，问题 0 项」。
```

### 经验 2：告诉它「照抄哪个文件」，别让它自己设计

AI 面对「帮我写个模块」会瞎设计；面对「照抄 `src/modules/feed/index.js` 的形状，把业务换成团队」会很准。

**每次开口就给它一个参照物。** 现在最好的参照物是这五个空壳文件（里面已经写好了注释和 TODO，说明这个模块该干什么、不该碰什么）：

```
src/modules/feed/index.js     ← P1 看这个
src/modules/doc/index.js      ← P2 看这个
src/modules/ai/index.js       ← P3 看这个
src/modules/team/index.js     ← P4 看这个
src/modules/ui/index.js       ← P5 看这个
```

**从头读一遍你那个文件**——里面已经把「归你什么、不归你什么、TODO 是什么、有什么坑」全写在注释里了。那是给你和给你 AI 的地图。

### 经验 3：明确告诉它「哪些文件你不许改」

AI 很爱「顺手帮你优化一下」。它会觉得 `src/core/guards.js` 里那个权限函数写得不够好，然后改了——然后 `check-golden` 就红了。

**每次任务开头都写上这句话：**

```
只允许修改下列文件，其它任何文件都不许改动：
- src/modules/<我的名字>/ 下的文件（可以新建）
- public/views/<我的新页面>.js（新文件）
- public/css/<我的样式>.css（新文件）
- scripts/<我的>-smoke.mjs（新文件）
- src/modules/index.js（只允许加一行注册）
```

### 经验 4：让它自己跑测试，别让它说「应该没问题」

AI 最喜欢说「这个改动应该没问题」。**三个字对付它：跑测试。**

```
你把上面改完，然后依次运行这三条命令，把完整输出贴给我：
node scripts/check-skeleton.mjs
node scripts/check-golden.mjs
node scripts/smoke.mjs
如果哪条红了，先别改代码，告诉我红在哪一行、为什么。
```

**这一条能挡掉八成的「AI 说好了其实没好」。**

### 经验 5：一个模块一个会话，写完就收

不要在一个 AI 会话里连写三个功能。上下文一长，它会忘掉前面定的契约，开始自己发明。**一个模块开一个会话，写完、测绿、提交，再开下一个。**

### 经验 6：卡住了，让它读测试的失败信息，不是让它猜

`check-golden.mjs` 红了会告诉你**第几条请求、期望什么结构、实际什么结构**。把这行原文贴给 AI，比描述「好像哪里不对」有用一百倍。

## 4. 怎么加一个新模块（照着抄就行）

### 4.1 后端：三步

**第一步：建目录。** `src/modules/<你的名字>/index.js`，抄 `src/modules/feed/index.js` 的形状。

**第二步：在 `install(ctx)` 里建表、登记路由。**

```js
export default {
  name: 'feed',
  apiPrefix: '/api/feed',
  owns: ['feed_items', 'feed_reactions'],
  reads: ['users', 'posts', 'follows', 'blocks', 'notifications'],
  install(ctx) {
    // 建表 —— 表名必须出现在上面的 owns 数组里，否则 check-skeleton 会报错
    ctx.schema.add('feed_items', `
      CREATE TABLE IF NOT EXISTS feed_items (
        id INTEGER PRIMARY KEY AUTOINCREMENT,
        user_id INTEGER NOT NULL REFERENCES users(id),
        body TEXT NOT NULL,
        scope TEXT NOT NULL DEFAULT 'public'
          CHECK (scope IN ('public','followers','team','private')),
        created_at INTEGER NOT NULL
      );
    `, 'feed');

    // 登记路由
    ctx.routes.add('GET', '/api/feed', async (ctx2) => {
      const user = await ctx2.guards.requireUser(ctx2);   // 未登录自动返回 401
      const rows = ctx2.db.prepare('SELECT * FROM feed_items ORDER BY id DESC LIMIT 20').all();
      ctx2.http.ok(ctx2.res, { items: rows, me: user.id });
    });
  },
};
```

**第三步：在 `src/modules/index.js` 的 `MODULES` 数组里加一项。** 这是全仓库唯一列举模块的地方。

> **⚠️ 两个 `ctx` 不是同一个东西。**
> `install(ctx)` 拿到的叫**模块上下文**（有 `schema`、`routes.add`、`db`、`store` 这些）。
> 路由 handler 里拿到的叫**请求上下文**（有 `res`、`req`、`user`、`http`、`guards`、`db` 这些）。
> 同名不同物，看 `src/core/context.js` 的定义。

### 4.2 前端：三步

**第一步：新建页面文件** `public/views/feed2.js`。

**第二步：在 `public/app.js` 里加一行 import，在 `public/core/router.js` 里加一段路由。** 这两处是「汇总点」，加一行就行——**加完记得 `check-ui-contract.mjs` 的 `MIN_UI_CHECKS` 可能要往上调**（见第 5 节）。

**第三步：样式写进 `public/css/31-feed2.css`**，并在 `public/style.css` 顶部加一行 `@import url('./css/31-feed2.css');`。

> 文件名前面的**两位数字决定样式生效顺序**。数字小的先加载，数字大的后加载、会盖住前面的。你在 `31-` 和 `41-` 之间插东西很方便，但**别改别人的分片文件**。

### 4.3 冻结的枚举（五个人用同一套，别各写各的）

```js
scope = 'public' | 'followers' | 'team' | 'private'
```

积木的顺序列 `document_blocks.position` 用 **REAL 浮点数**——想在 1 和 2 之间插一块就写 `1.5`，不用把后面所有块重排。这是 P2 定、其他人跟着用。

## 5. 怎么知道「我没改坏东西」

### 5.1 现在这套测试在守什么

| 脚本 | 守什么 | 现在的成绩 |
|---|---|---|
| `check-golden.mjs` | **行为金标准**：96 条固定请求的**状态码 + 响应结构**指纹 | 96 项，差异 0 |
| `check-skeleton.mjs` | 骨架本身：模块能不能单独拆掉、薄入口有没有变胖、表归属对不对 | 47 项 |
| `check-frontend.mjs` | **前端整页渲染**：34 个页面在最小 DOM 垫片里全部渲染成功 | 34/34 |
| `smoke.mjs` | 后端端到端（起真服务器打接口） | 253 项 |
| `smoke-ai.mjs` | AI 接口端到端 | 61 项 |
| `feed-smoke.mjs` / `doc-smoke.mjs` / `team-smoke.mjs` | 动态流 / 积木 / 团队的接口端到端 | 95 / 469 / 190 项 |
| `check-ui-contract.mjs` | 前端类名 / API 字段 / 主题 / 头像 / 角色 / 私信 / 团队 / 剪贴板 / 公式结构 | 258 项 |
| `check-encoding.mjs` | 编码体检（BOM / 乱码 / 关键中文片段） | 194 文件 / 87 断言 |
| `check-notes-ui.mjs` | 笔记的前端结构 | 33 项 |
| `notes-smoke.mjs` / `forum-ai/selftest.mjs` | 笔记 / AI 子系统 | 44 / 92 项 |
| `note-agent/scripts/run-tests.mjs` | note-agent | 只在这台机器跑不了（沙箱限制），CI 上是绿的 |

**为什么 `check-golden` 是最重要的那条？** 因为它**只比结构、不比内容**——它记录的是「第 37 条请求：`POST /api/posts`，状态码 200，返回的对象有 `ok`/`data`，`data` 里有 `post`，`post` 里有 `id`/`title`/…」，而不是「标题正好是『你好』」。

这样做的好处：**你加功能不会让它红，你改坏旧功能才会让它红。** 它守的是「五个人折腾完之后，老用户感觉不到任何变化」。

### 5.2 「不下降哨兵」是什么，为什么要管它

`check-encoding.mjs` 里有个常量叫 `MIN_CHECKED = 194`，意思是「**至少要检查 194 个文件**」。

为什么需要它？假设你把 `public/views/user.js` 改名成 `public/views/profile.js` 却没更新检查脚本——脚本不会报错，它只是**少检查一个文件**，然后照样打印「✅ 全部正常」。测试变绿了，但漏洞变大了。这比测试变红危险得多。

所以改造时加了三道哨兵：

- `check-encoding.mjs` → `MIN_CHECKED`（文件数下限）+ `REQUIRED_FILES`（关键文件必须存在）
- `check-ui-contract.mjs` → `MIN_UI_CHECKS`（断言数下限）
- `check-notes-ui.mjs` → `MIN_PASS`

**你要做的事：你新增或搬动文件之后，主动把对应的下限往上调。** 比如你建了 `public/views/doc.js`，就在 `check-encoding.mjs` 的 `REQUIRED_FILES` 里加上它、把 `MIN_CHECKED` 加 1。**这不是额外负担，这是你自己的安全带。**

### 5.3 前端改完还要跑这个

```bash
node scripts/check-frontend.mjs
```

它会在一个假 DOM 里把 18 个页面**全部渲染一遍**。你的新页面漏了字段、拼错函数名、import 路径写错，它一次全给你指出来（浏览器里你只能看到一行红字）。

它用的假数据是**从真服务器采回来的真响应**（存在 `scripts/frontend-fixtures.json`）。如果你改了接口的返回结构：

```bash
node scripts/capture-fixtures.mjs && node scripts/check-frontend.mjs
```

## 6. 提交和合并

### 6.1 提交前自检（缺一条都不许提交）

- [ ] 我跑过 `check-golden`，是绿的 —— **没改坏现有行为**
- [ ] 我跑过 `check-skeleton`，是绿的 —— **我的模块能被单独拆掉**
- [ ] 我跑过 `smoke` 和我自己的测试，是绿的
- [ ] `git diff --name-only` 看一遍：**里面没有别人的目录**
- [ ] 我改了接口返回结构的话，重跑过 `capture-fixtures` 并更新了 `frontend-fixtures.json`
- [ ] 我新增了文件的话，**把哨兵数字往上调了**（见 5.2）
- [ ] 未登录访问我的接口返回 **401，不是 404**（这是现有行为，别"顺手修"）
- [ ] 我提交里**没有 API key、没有 token、没有 `.env`**

### 6.2 分支纪律

```bash
git checkout -b feat/feed          # 从 v2-skeleton 开你自己的分支
# ... 干活 ...
git push -u origin feat/feed       # 推你自己的分支
```

**永远不要** `git push origin main`，也不要合并进 `main`。理由看第 1.1 节——服务器会自动部署 `main`。

### 6.3 合并顺序

**P2 → P1 → P5 → P3 → P4。**

理由：先把表结构最稳的合进去（P2 的积木是地基），最后合最容易和界面打架的（P4）。P5 要早点合，因为其他人要用它的界面零件。

好在每一路的合并在 `src/modules/index.js` 里**只占一行**，所以合并本身很简单——难的是每个人别去碰别人的东西。

### 6.4 三个会拖你后腿的坑

**坑 1：`deploy.sh` 的白名单。**

服务器上的部署脚本**只替换 `src/ public/ scripts/` 三个目录**。你要是新开一个顶层目录（比如 `api/`），代码推上去了但**不会被部署**——然后 `src/server.js` 引用一个不存在的文件，服务起不来，健康检查失败，自动回滚。

**所以：新模块必须放在 `src/modules/` 里面，不要新开顶层目录。** `public/` 不用管，静态文件是「从磁盘按路径读」的，新子目录自动能访问。

**坑 2：删板块会灌假数据。**

现在的代码判断「这是不是一个新库」的方式是**看板块表空不空**。所以如果你把板块全删了再重启，它会以为这是个新库，然后**往你的真库里灌 4 个假账号（admin / alice / bob / carol）+ 8 篇假帖子**。动 `boards` 表之前先想清楚。

**坑 3：不要用 `node --test`。**

Node 自带的测试 runner 会 spawn 子进程用管道收输出，在某些受限环境下会 `EPERM` 失败。**照抄现有测试的写法**：自己起一个临时端口、临时数据库的服务器，自己数断言，最后打印「通过 N 项，问题 0 项」。
