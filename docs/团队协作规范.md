# 团队协作规范

> 这份是**硬规矩**，不是建议。第 2 节的红线，违反一次就可能让别人半天的工作白做。
>
> 想了解「为什么这么分工」「怎么让 AI 帮你写」看 `06-五路并行开工教程-人话版.md`。

---

## 0. 三句话版本

1. **永远不许 `git push --force`**
2. **永远不许直接推 `main`**
3. **只改自己名下的文件**

把这三条记住，剩下的都是细节。

---

## 1. 仓库与分支

仓库地址：<https://github.com/RyuriHime/Blog>（公开仓库，任何人可读；只有协作者能推）

| 分支 | 是什么 | 谁能推 |
| --- | --- | --- |
| `main` | 线上版本。服务器每 3 分钟自动拉取并部署 | **谁都不许推** |
| `v2-skeleton` | 大家共同的开发基线，所有人都从这儿开分支 | **谁都不许推** |
| `feat/feed` | P1 动态流 | P1 |
| `feat/doc` | P2 积木帖子 | P2 |
| `feat/ai` | P3 AI | P3 |
| `feat/team` | P4 团队 | P4 |
| `feat/ui` | P5 界面 | P5 |

**只往自己那条 `feat/*` 推。** 别人的分支也别去动 —— 技术上大家都是协作者、都推得动，但推了等于替别人写代码，出了事算谁的说不清。

## 2. 红线：违反一次就可能让别人白干

| # | 不许 | 为什么 |
| --- | --- | --- |
| 1 | `git push --force` / `-f` / `--force-with-lease` | **这是唯一能真正抹掉别人提交的操作。** 正常的 `git push` 是推不动就报错（`non-fast-forward`），**不会覆盖**。所以要覆盖只能靠强推 —— 别用 |
| 2 | `git push origin main` | 服务器盯着 `main`，推上去 = **你直接改了线上网站** |
| 3 | 推 `v2-skeleton` | 那是五个人的公共基线，谁都能推等于谁都能改别人的起点 |
| 4 | 改 `src/core/` 或 `src/modules/core/` | 全站地基。`check-golden` 的 96 项行为指纹守的就是它，动它全队遭殃 |
| 5 | 改别人目录里的文件 | 合并时必打架。`git diff --name-only` 里出现别人的目录 = **停下来，先问** |
| 6 | 提交 API key / token / `.env` | **仓库是公开的。** 推上去等于公开泄密，而且**永远删不掉** —— 历史里一直有，改密码也救不回已泄露的那份 |
| 7 | 自己 `CREATE TABLE` / 自己连数据库 | 表归属是分配好的，建表走 `ctx.schema.add()`，别绕过去 |
| 8 | 自己发明接口返回格式 | 全站冻结成 `{ ok: true, data }` / `{ ok: false, error: { code, message } }` |
| 9 | 新开顶层目录 | 部署脚本只替换 `src/` `public/` `scripts/` 三个目录 —— 新目录推上去**不会被部署**，服务会起不来 |
| 10 | 用 `node --test` 写测试 | 它在受限环境下会 `EPERM`。照抄现有测试的写法（自己起临时端口、临时库、自己数断言） |

## 3. 日常操作（照抄即可）

### 3.1 第一次：把代码拿到手

```bash
git clone https://github.com/RyuriHime/Blog.git
cd Blog
git switch -c feat/team origin/v2-skeleton     # 把 feat/team 换成你自己那条
```

`git switch -c` 的意思是「新建一条分支并切过去」，`origin/v2-skeleton` 是它的起点。

> 连不上 GitHub？先开代理，然后：
> `git config http.sslBackend openssl` 和 `git config http.proxy http://127.0.0.1:7890`
> （端口换成你自己代理的端口。Windows 下 git 自带的 schannel 经常报 `SEC_E_NO_CREDENTIALS`，换 openssl 就好。）

### 3.2 每天开工前，先把别人的进度合进来

```bash
git switch feat/team                  # 确认在自己分支上，别在 main 上干活
git fetch origin
git merge origin/v2-skeleton          # 把公共基线的更新并进来
```

**每天开工前做一次。** 攒一星期再合，冲突会多到想哭。

### 3.3 起本地服务看看

```powershell
# Windows PowerShell
$env:PORT='3511'; $env:DB_FILE='data/p4.db'; node src/server.js
```

```bash
# macOS / Linux
PORT=3511 DB_FILE=data/p4.db node src/server.js
```

打开 <http://127.0.0.1:3511>，演示账号 `admin` / `admin123`。

**每人用不同的 `DB_FILE`**，别去动别人的 `data/*.db`。

### 3.4 提交前必跑

```bash
node scripts/check-golden.mjs      # 没改坏现有行为
node scripts/check-skeleton.mjs    # 我的模块能被单独拆掉
node scripts/smoke.mjs             # 接口冒烟
node scripts/check-frontend.mjs    # 改了前端就跑
node scripts/check-encoding.mjs    # 中文没乱码
```

**全绿才能提交。** 红了先修，不要「先提交再说」。

### 3.5 推上去

```bash
git add -A
git commit -m "P4：建 teams / team_members 两张表"
git push -u origin feat/team
```

## 4. 提交前自检清单

- [ ] `check-golden` 绿 —— 没改坏现有行为
- [ ] `check-skeleton` 绿 —— 我的模块能被单独拆掉
- [ ] `smoke` 和**我自己写的测试**绿
- [ ] `git diff --name-only` 看过一遍：**里面没有别人的目录**
- [ ] 改了接口返回结构的话，重跑 `capture-fixtures` 并更新了 `frontend-fixtures.json`
- [ ] 新增了文件的话，**把哨兵数字往上调了**（见教程 5.2）
- [ ] 未登录访问我的接口返回 **401，不是 404**（这是现有行为，别「顺手修」）
- [ ] 提交里**没有 API key、没有 token、没有 `.env`**
- [ ] 我**没有** force push，**没有**碰 `main`

## 5. 合并规矩

合并顺序：**P2 → P1 → P5 → P3 → P4**

理由：先把表结构最稳的合进去（P2 的积木是地基），最后合最容易和界面打架的（P4）。P5 要早点合，因为别人要用它的界面零件。

好在每一路在 `src/modules/index.js` 里**只占一行**，所以合并本身很简单 —— 难的是每个人别去碰别人的东西。

**合并由一个人统一做，不许自己把自己的分支合进公共基线。** 想合并了就在群里说一声。

## 6. 上线规矩（这条最要紧）

- 服务器上有个定时任务，**每 3 分钟**拉一次 `main` 并部署到真实线上。
- 拉了之后**先跑 CI**：`.github/workflows/checks.yml` 那套测试。
  **测试不过就不部署**，线上继续跑上一个好版本 —— 这是自动的，不用你操心。
- 部署时先备份、健康检查（20 秒不通就**自动回滚**），备份在 `/opt/deploy/backups`。

**推论：谁能推 `main`，谁就能往线上跑任意代码。** 所以规矩是「谁都不推 `main`」。

> ⚠️ **当前的一个特殊情况（暂时）**
> 线上现在跑的是 `v2-skeleton` 的代码（手工部署的），而自动部署盯的还是 `main`。
> 也就是说 **现在推 `main` 会把线上打回旧版**。
> 等 `v2-skeleton` 正式合进 `main` 之后，这条注意事项自然消失。

## 7. 出错了怎么救

| 症状 | 原因 | 怎么救 |
| --- | --- | --- |
| `! [rejected] ... (non-fast-forward)` | 别人先推了，你落后了 | `git fetch origin` → `git merge origin/feat/xxx` → 解冲突 → 再推。**千万别用 `-f` 绕过** |
| `error: failed to push some refs` | 同上 | 同上 |
| 推上去了但内容不对 | —— | 不用慌，再推一个「改回来」的提交：`git revert <sha>` 然后正常推。历史都在，一个字没丢 |
| 不小心推了 `main` | —— | **立刻在群里说 + 告诉负责人。** 线上会被自动部署，但有 CI 门禁和自动回滚兜着，先别自己乱操作 |
| 已经 force 推了，把别人的提交冲掉了 | —— | **能救。** 谁本地还有那个提交，谁就能推回去：`git push origin <那个提交的sha>:refs/heads/分支名`。**先别关电脑、别删本地仓库** |
| 本地改乱了，想回到干净状态 | —— | 先 `git status` 看清楚。`git stash` 暂存，或 `git checkout -- .` 丢弃（**会丢未提交的改动，确认了再用**） |
| 合并冲突不会解 | —— | **别硬解。** 把冲突的文件和报错原样贴出来问 |
| 起服务报 `MODULE_NOT_FOUND` | —— | 十有八九是**不在仓库根目录下跑的**。`cd` 到 `Blog/` 再跑 |

**核心认知：只要还有一个人本地留着完整的 `.git`，就丢不了东西。** 所以出事了第一件事是**别关电脑、别删本地目录**，然后问人。

## 8. 冻结的四样契约（谁都不许改）

| 冻结的东西 | 值 |
| --- | --- |
| 可见范围枚举 | `'public'` \| `'followers'` \| `'team'` \| `'private'` |
| 块位置类型 | `document_blocks.position` 用 `REAL`（插在中间写 `3.5`） |
| 接口信封 | `{ ok: true, data }` / `{ ok: false, error: { code, message } }` |
| 页面地址 | 旧地址必须还能打开；`#/post/:id` 这类帖子地址改为**重定向到对应的积木 doc**（不是 404）；`#/new`、`#/edit/:id` 同样改道到积木广场与对应积木的编辑器 —— `#/u/:username`、`#/settings` … 照旧 |

改这四样 = 改需求，要全队同意，并且要同步改 `docs/skeleton.md` 和测试。
