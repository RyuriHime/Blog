**1. `/turn` 静默失效（最严重）。** 真机模型回的字段名与提示词约定不一致：它写 `{"op":"replace","target":"b2","after":"新正文"}`，而 `validateOp` 只认 `kind` + `text`，于是**每一条**都落进 `skipped: unknown_kind` —— 用户提了要求、面板显示"已处理"，草稿一个字都没改。修法是把同义键名归一化（`note-agent/src/ops.mjs` 新增 `KIND_ALIASES` / `TEXT_ALIASES` / `TITLE_ALIASES` 与 `normalizeOp`，`validateOp` 回传归一化后的 op，正式写法优先），而不是放宽校验。真机复验：同一条要求现在返回 2 条 `replace`，`skipped` 为空。

## 交付后：第三轮真机验收又查出两处（已修，全部有测试）

**4. `cleanOps` 把别名兼容架空了（第二处静默失效）。** `note-agent/src/orchestrator.mjs` 的 `cleanOps` 原本写 `return verdict.ok ? op : {…}` —— 回传的是 **`validateOp` 的原始输入**而不是归一化结果，于是问题 1 里刚做好的键名归一化在真实路径上一点没生效。真机证据：落库 `notes_messages` 里两条 op 是 `{"target":"b2"}` / `{"target":"b7"}`（`kind` 为 `undefined`、`text` 为空），而 `skipped` 是 0 —— 又一次"面板说处理好了、草稿没动"。改成 `return verdict.ok ? verdict.op : { kind: rawKindOf(op), __invalid: verdict.reason, target: op?.target ?? op?.after }`，并让 `ops.mjs` 新增 `export function rawKindOf(op)`（尽量还原模型写的指令名，供面板显示"第几条指令没生效"）。真机复验：两条 op 都是正式 `{"kind":"replace","text":"…"}`，`skipped` 为空。

## 验收操作教训：改了后端代码必须重启验收服务（重要）

第四轮真机验收时踩到一次**假故障**：`/turn` 落库的 `ops` 里 `kind` 是 `undefined`、`skipped` 却是 0，看起来像新写的归一化完全失效。实际原因是端口 3456 上跑的仍是 `cleanOps` 修复**之前**启动的那个 node 进程（pid 57300，起于 10:52:44）—— `.tmp-srv2.ps1` 起的 node 会脱离 pwsh 作业继续存活，所以"重新跑脚本"并不等于"跑的是新代码"。

判定手法（两步，都很快）：
1. `.tmp-probe-db.mjs`：用 `node:sqlite` 的 `DatabaseSync` 直读 `data/acceptance2.db`，打印 `notes_messages` 里每轮的 `ops` / `skipped` 原文与 `notes_reviews` 的 severity 分布 —— 先确认落库形态到底长什么样。
2. `.tmp-probe-api.mjs`：`fetch` 登录取 cookie 后 `GET /api/notes/session/<id>`，打印 HTTP 返回里的 `messages[].ops` —— **这一层才是判定"端口上是旧代码还是新数据"的关键证据**（库里是旧数据、接口回旧形状，就说明进程没换）。

清进程：`Get-NetTCPConnection -LocalPort 3456 -State Listen` 找到 `OwningProcess` 再 `Stop-Process -Force`。看到 `EADDRINUSE` 就是这个信号。

**规矩**：每次改完 `note-agent/src/**` 或宿主后端代码，先杀掉监听端口的旧进程、重启、然后**发一次真实请求核对落库/返回形态**，再开始判断功能对不对。

## 交付后：第四轮真机验收查出的问题（已修，有测试）

**6. `/review` 稳定 502：模型把未转义的双引号写进了 JSON 字符串值。** 真机点「学术审查」必现 `{"ok":false,"error":{"code":"ai_bad_json","message":"模型没有返回可解析的 JSON，请重试"}}`（HTTP 502，耗时 38s）。探针 `.tmp-probe-review-raw.mjs` 直接调 `chat()` 拿到原文后定位：首轮 `finish=stop`、`usage={"prompt":532,"completion":6469}`、`textLen=2291`、花括号 `{=13 }=13` **完全平衡**、无 ``` 围栏，但 `extractJson` 返回 null —— 因为模型写了 `"…但作为一篇题为"导数与积分"的笔记，第二节"积分"只有一句概括…"`，**字符串值内部的引号没转义**。这不是"截断"，重试机制也救不了第一次（收紧提示后的第二轮 `completion=2944` 能解析，findings=5）。

修法是新增 `note-agent/src/json.mjs` 的 `extractJsonTolerant(text)`，在 `forum-ai` 的 `extractJson` 失败后做一次**保守重写**再解析：字符串外数括号深度；字符串内只承认 `\` 后跟 `" \ / b f n r t u` 的转义，其余裸反斜杠补成 `\\`（保住 LaTeX）；裸 `"` 只有"跳过空白后是 `:`/`,`/`}`/`]` 或已到文本结尾"才算结束引号，否则补成 `\"`；裸 `\n`/`\r`/`\t` 转义；**结尾括号不平衡或仍在字符串内一律返回 null**。铁律不变：宁可报错，绝不放行猜出来的内容。顶层是数组也一律拒绝（`JSON.parse` 会把它当"解析成功"，下游只会拿到 `parsed.findings === undefined` 而不报错）。

`note-agent/src/review.mjs:11` 与 `note-agent/src/orchestrator.mjs:12` 改成 `import { extractJsonTolerant as extractJson } from './json.mjs';`，调用点一行未改。
对应测试：`tests/test-json.mjs`（新文件，17 条）—— 内含真机原文常量 `REAL_BAD`，断言标准解析器确实救不了它、容错解析能救回来、引号与 `$x_0$` 的反斜杠都原样保留、findings 一条不少；以及截断/未闭合/顶层数组必须返回 null、救回来的对象能再次序列化解析。
